# 2026.243.1627 — fix(resolve): the resolved-project cache key ignored the scan scope

## Summary

A deploy's `add_candy:` refs reach the resolved-project envelope through
`ResolvedProjectRequest.ExtraCandyRefs`, which widens the candy scan. `refs_collect.go`'s own
comment records that widening as a previously-fixed regression — "the host's own scan and this
envelope re-fetch used to run independently, so a remote add-candy resolved host-side never
reached here at all".

The persistent resolved-project cache re-opened the same hole one layer up. `projectCacheKey`
hashed `<dir>:<sha256(charly.yml)>` and nothing else, so every request for a project shared ONE
cache slot no matter how it had widened the scan. A resolve widened for one ref was served an
envelope resolved for a different one, and the compile failed:

```
fleet compile: candy "@github.com/opencharly/plugin-quickshell/candy/plugin-quickshell:v2026.243.1516"
  not in resolved-project envelope
```

A candy reachable ONLY through `add_candy:` — the documented way a host-side plugin rides into a
bed — could therefore never be compiled into a deploy.

### Root cause, measured

The cached envelope on disk held 167 candies. `plugin-quickshell` was absent from all of them,
and the entry's key carried no trace of any widening:

```
key: /…/distro-omarchy:b5a362cc3d6e14b8056ee34bab676691cc
candies in cached envelope: 167
  plugin-quickshell present: []   (only the unrelated layer-omarchy-shell/omarchy-quickshell)
```

The widening was computed correctly, then discarded by a cache that could not tell two different
scans apart.

### The fix

The key now carries every request field that changes what the resolve PRODUCES rather than what
it costs: `ExtraCandyRefs`, `RequestedBoxes`, `IncludeDisabled`, and `LocalSuperproject` (which
applies a `CHARLY_REPO_OVERRIDE` around the resolve, so it decides whether refs come from the
local superproject or the fetch cache). Refs and boxes are sorted before joining, so the same
scan requested in a different order still hits one entry.

The single-slot file becomes a bounded 16-entry map. With a scope-carrying key a project
legitimately has several live entries at once — an unwidened `charly status` resolve plus one per
`add_candy` ref a deploy compiles — and a single slot would make each write evict the last,
re-resolving the whole project every time. That would trade a correctness bug for a performance
one.

## Rulebook compliance

- **R0 — Skills first.** The dispatcher's `git-workflow` and `root-cause-analyzer` rows matched
  (a PR-landing change, opened by a failure) and were loaded before the first tool call.
- **R1 — RCA every anomaly.** The envelope failure was root-caused to the cache key before any
  change. Three earlier hypotheses (missing root `charly.yml`, missing umbrella submodule, tag
  content) were each measured and DISCARDED rather than stacked; the cache-key finding came from
  reading the error site and then the cache file on disk.
- **R2 — Finish the whole cutover.** Nothing parked. Every field that changes what the resolve
  produces is in the key (`ExtraCandyRefs`, `RequestedBoxes`, `IncludeDisabled`,
  `LocalSuperproject`), not just the one that caused the reported failure; `projectCacheKey` has
  a single call site and it is updated. No "pre-existing" or "follow-up PR" split — the gofmt
  drift in two untouched files is fixed here rather than left.
- **R3 — No duplication.** One key derivation, one cache reader/writer pair; no second cache and
  no parallel scope-tracking mechanism introduced.
- **R4 — No workarounds.** The cache is not disabled, TTL'd to zero, or bypassed for widened
  requests — it is keyed correctly. **R4a**: the product is fixed; no doc note routing around it.
- **R5 — Delete legacy completely.** The single-slot `projectCacheFile{Key,Resolved,Project}`
  shape is REMOVED, not left beside the map. An old-shape file on disk unmarshals to zero entries
  and is a clean miss, so no migration path is left behind either.
- **R6 — Preserve user work and Git safety.** `git status` inspected before committing; feature
  branch, no force-push, no `--no-verify`, no direct push to `main`. One self-inflicted incident
  is disclosed: I created `resolve_project_cache_test.go` with `cat >` without checking it
  existed, overwriting 56 lines from the PR that introduced this cache. Both original tests are
  recovered from `git show HEAD:` and restored in this diff (adapted to the new API), so no
  coverage is lost.
- **R7 — Prove behavior, not compilation.** `TestProjectCacheKeySeparatesScanScope` fails on all
  five scope fields when `projectCacheKey` is reverted to the old derivation — pasted verbatim in
  *How tested*. Coverage that cannot fail would have proved nothing here, which is the exact trap
  this bug lived behind.
- **R8 — Preserve emitted artifacts.** The resolved-project envelope is the emitted artifact and
  it is validated end to end: the bed's compiled deploy plans now contain the add_candy candy, and
  `check-live` / `check-live-rebuild` both report `106 steps: 104 passed, 0 failed, 2 skipped`.
  The 2 skips are the autologin candy's mutating `run:` steps, correctly skipped in verify-only
  mode.
- **R9 — Binary equals source.** charly was rebuilt from this tree with `task build:binary`
  (CalVer-stamped `2026.243.1302`), not a plain `go build` — charly's own freshness gate refused
  the unstamped binary first, which is how this was caught. The compiled-in fix was verified by
  symbol presence (`evictOldestProjectCacheEntries`) before the bed was run.
- **R10 — Fresh disposable proof.** `check-omarchy-desktop-vm` is `disposable: true`; the full
  sequence ran including `update` (destroy + rebuild, 5m3.242s) and `check-live-rebuild`
  (1m15.67s) against a guest built from nothing — identical 104/106 to the live pass.
