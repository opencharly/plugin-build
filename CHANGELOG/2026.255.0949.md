# 2026.255.0949 — fix(build): emit the store-bloat nudge as an ADVISORY (notice:), not a warning

## Summary

Emit the podman store-size nudge as an **advisory** (`notice:`) instead of `warning:`, and name the functions to match.

### The RCA — why this line must not be classified as a change-defect warning

The nudge's SUBJECT is the **build host's** podman store, not the change under test:

```console
$ podman system df
TYPE           TOTAL       ACTIVE      SIZE      RECLAIMABLE
Images         1579        43          128.1GB   93.76GB (73%)
```

That is a property of the machine the build runs on. It is inherited by EVERY bed, EVERY PR, and every operator build on that host — no PR under review can fix it, and no PR's correctness depends on it. Classifying it as a change-defect `warning:` means the check gate fails on a condition of the runner rather than on the change, which is the category error the third diagnostic tier exists to remove.

**This is not a hypothesis — it is the observed cause of three blocked PRs.** The validator's own review of `distro-cachyos#83` lists it among the surviving warnings blocking that PR: *"two un-allowlisted classes survive the PASS run (14× `candy pod-postgresql resolved to multiple versions`; 1× `podman store is bloated`)"*; `plugin-check#47` was blocked for the same class; and `pod-immich-ml#5` for the same. One host-state line is gating three unrelated PRs.

**The emitter's own source, from `main`, documents the line as a non-blocker** (`candy/plugin-build/store_bloat.go`, the doc comment on `noticeIfStoreBloated` — quoted verbatim):

> `// noticeIfStoreBloated runs \`podman system df --format json\` and, when the store's reclaimable`
> `// bytes exceed storeBloatReclaimableThreshold, prints a warning naming the purge that addresses`
> `// it (\`charly clean --deep\`). It is fail-soft by design: a store probe that fails (podman absent,`
> `// non-JSON output, no Images entry) is skipped silently — the warning is a hygiene nudge, never a`
> `// build blocker (R4: no retry loops, no sleeps; the probe runs exactly once per build drive).`

*"never a build blocker"* — the producer already declares the tier it means. Emitting that at `warning:` severity contradicts the producer's own contract; this PR makes the label agree with it.

### What this does NOT do

It does not hide the condition and does not weaken any real check: the line stays **reported** (the scanner's companion `plugin-check#48` counts it as `advisories: N` and prints `advisories_fatal: false`), and the remediation (`charly clean --deep`) stays in the text. `error:` lines still hard-fail; real `warning:` lines still count and still fail when staged fatal. The bloat condition itself remains tracked as the overlay-store corruption class in `opencharly/charly#173` — this PR does not claim to have fixed the host's store, and does not need to: it stops a host-state report from masquerading as a defect in the change under test. **Because this alters the effective behaviour of the check gate, it requires the T4 maintainer sign-off, which is recorded in a PR comment below.**

### Landing order — this PR must land AFTER `plugin-check#48`, never before

Under `main`'s scanner there is no advisory tier at all, so a `notice:`-prefixed line matches **no** recognizer and is silently IGNORED. Relabelling first would therefore not move the line from "warning" to "counted advisory" — it would move it from **reported** to **invisible**, which is precisely the silent-drop risk the review named. The scanner change is the prerequisite, not a sibling:

1. **`plugin-check#48`** (the third tier + the `notice:`/`advisory:` recognizer) — the line stays REPORTED, now as an advisory.
2. **this PR** (the producer label) — the line is emitted in a class the scanner already understands.

#48's tests pin exactly the contract this depends on: the producer's real line shape classifies as `severityAdvisory`, is counted in `Advisories` (step AND run), and never fails under any policy. The order is a hard requirement of this change, not a nicety — and the live A/B below was run with BOTH branch sources loaded for that reason.
