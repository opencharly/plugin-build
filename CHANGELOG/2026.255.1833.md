# Remove the podman store-size rule at its source

## Authorization — maintainer/operator sign-off (verbatim)

> "these podman storage rules are utter bullshit that must be removed !!!"

## Summary

### RCA — why the rule must not exist

`candy/plugin-build/store_bloat.go` ran `podman system df --format json` once per build drive (call site: `drive.go` → `runBoxBuild`) and printed a line whenever the **local BUILD HOST's** podman store had more than 50 GiB reclaimable. The org-wide R10 gate counts **un-allowlisted diagnostic lines in a bed's own output**, so a property of the machine — nothing to do with the change under test — could gate an unrelated PR. It did, simultaneously: `pod-immich-ml#5`, `distro-cachyos#82`, `distro-cachyos#83`, `plugin-check#45`, `plugin-check#46`, `plugin-check#47`.

The rule then forced one of exactly two bad responses:

1. **Purge the store** — which deletes the untagged intermediates that ARE buildah's layer cache. Measured on this host: a warm cachyos box build is **96 s**; a cold one is **1429–2203 s**.
2. **Weaken the gate** with a consumer-side allowlist entry (`plugin-check#47`, `feat/allowlist-podman-store-bloat-nudge`) — correctly rejected on review as a gate-loosening; that PR is CLOSED.

The emitter's own doc comment already declared the line *"fail-soft by design … a hygiene nudge, never a build blocker"*. A behaviour documented as a non-blocker must not exist in a form that can gate a merge — and relabelling its severity (#11) only tunes the label: the host-state line still lands in every bed's output. This PR deletes it at the source.
