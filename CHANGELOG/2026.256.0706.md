# 2026.256.0706 — fix(build): the per-image build lock queues — name the image and the holder

## Summary

This is the **call-site half** of the fix for the measured `#83` block:

```
charly: error: command "build": building githubrunner: acquiring build lock for githubrunner:
flock /home/atrawog/.cache/charly/locks/image-abNcNfNcNaeN.lock: lock held by another process for > 2m0s
```

(check run `2026.255.2310` — a peer was COLD-building the same image; a legitimate hold, not a stuck one.)

### The primitive

Bumps `github.com/opencharly/spec` **v0.2026250.523 → v0.2026256.653** (spec #132, merged). That release makes every **blocking** acquire of `spec/lock`'s advisory flock **queue behind a contended lock with a bounded, REPORTED wait**: it says who holds the lock while it waits, and if the bound is ever reached it fails with the **holder's pid + command line** (resolved from the kernel — never from lock-file bytes) plus the next step. Previously it gave up after **2 minutes and named nobody**, which is shorter than one cold image build (~26 min measured) — so the second of two concurrent builders of the same image took a hard failure instead of cache-hitting once the peer finished.

### The call site (this repo)

The failure is now rendered by `imageBuildLockError(box, err)`, which adds what the primitive cannot know:

- **WHICH box** and **the LOCK KEY** — the FULL tag, whose tag-stripped ref is what the lock file hashes, so the contended artifact is identifiable;
- **what to do** — wait for the peer, re-run, and the second build cache-hits;
- and the primitive's error stays **wrapped (`%w`)**, so `errors.Is`/`As` still reach it.

The composed message, from the test below:

```
acquiring the per-image build lock for githubrunner (ghcr.io/opencharly/githubrunner:2026.256.0655):
flock /home/u/.cache/charly/locks/image-ab5c861f713c0ae3.lock: still held by pid 4242
(/usr/local/bin/charly box build cachyos) after 30m0s — that process is still running; wait for it to
finish and retry (the kernel releases the lock when it exits, so there is nothing to clean up)
— another charly process is building this image; wait for it to finish and re-run (the second build then cache-hits)
```

One incidental fix, called out rather than hidden: `advisory_sink_test.go`'s unchecked pipe `Close` (`errcheck`) — found by the local lint run, PRE-EXISTING on `main` (last touched by PR #7, not in this diff). It is fixed here (one line) rather than reported as "out of scope" (R1), so the lint gate is green instead of carrying a known red line.

### Consumer follow-on (NOT in this PR)

The compiled-in path reaches this candy through **`opencharly/charly`'s `go.mod` require** (`github.com/opencharly/plugin-build/candy/plugin-check…` → `plugin-build v0.2026255.1833`), so a **plugin-build pin bump in charly** lands as its own PR once this merges — same discipline as the spec bump that already landed for spec #132. Until then, charly binaries built from `main` keep the old message (and the old bound).

They belong to the pinned release: **[opencharly/spec#132](https://github.com/opencharly/spec/pull/132)** (merged, validator PASS) pastes a live external-holder run — a real `flock` holder for 40 s, and the waiter printing the waiting report then acquiring on release (`waiter: ACQUIRED (queued) after 40s`), plus its timeout error naming the holder and its own package tests (still no lock-file content). This PR pins that release and makes the call-site message carry the image identity through it.
