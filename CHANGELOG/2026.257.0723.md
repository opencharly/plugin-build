# 2026.257.0723 — fix(build): content-address the resolved-project cache key over discovered manifests

## Summary

Fix the resolved-project cache KEY so it covers every input the resolve reads — including manifests that appear or change in the tree — and drop the TTL in favour of content addressing. This is the root fix for the eval-lane `charly check run: no entity "check-omarchy-pr-<N>-vm"` failures.

### The bug (reproduced, then fixed)

`projectCacheKey` hashed only the **top-level `charly.yml`** bytes + dir + scan scope, with a **5-minute TTL**. The eval lane RENDERS each per-PR bed into a discover root (`pr-beds/**`) **during** its run. So the first resolve cached a **skeleton** envelope (beds not yet written); every later lane's resolve hit that still-"fresh" entry, whose `Deploy` map has no `check-omarchy-pr-<N>-vm` entity → **`no entity`**.

### The fix

`projectCacheKey` now folds the **bytes of every `charly.yml` manifest under the project root** into the digest, and the **TTL is removed** (validity is the content key — the Docker model). The digest is **interpretation-free** (no `discover:` parse) and applies the ONE canonical skip rule the discover walk uses (`kit.DiscoverSkipDir`). It is **fail-closed** at the key AND the read/write helpers: an un-enumerable tree yields an empty key, `readProjectCache` misses and `writeProjectCache` is a no-op.

An earlier PR (plugin-pipeline#22) blamed this on torn bed writes; that RCA was WRONG and is **closed**.
