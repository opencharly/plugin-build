# 2026.276.0438 — fix(deps)!: adopt the typed ExtraCandyRef (spec#188 consumer)

## Summary

Adopts `spec v0.2026273.203` + `sdk v0.2026276.48`, which is the type change `spec#188` made: an `ExtraCandyRef` now carries its **SCOPE**, so `spec.ResolvedProjectRequest.ExtraCandyRefs` is `[]spec.ExtraCandyRef{Ref, Scope}` instead of `[]string`.

**Why this repo is in the wave.** Every compiled-in plugin candy is a `require` pin in charly's `go.mod`, resolved from the module proxy, so when `sdk`'s own main moved its `spec` require to `v0.2026273.203` (`sdk#325`, merged), any charly that adopts that sdk stops compiling this candy. `plugin-build`, `plugin-fleet` and `plugin-installstep` are the three; this is the `plugin-build` leg.

**The change.** `projectCacheKey` folds the widened add_candy scope into the resolved-project cache key:

1. **`resolve_project_word.go` (+6/−1)** — the key used to copy `ExtraCandyRefs` into a `[]string` and sort it. A ref's scope is part of its identity (`sdk#325` consumes exactly that, and `spec.ScopeIsBox` is the predicate that decides which version differences are genuine conflicts), so the scope is part of the key too: each ref contributes `Ref` **and** `Scope`, and the list is still sorted. The sort/join shape is unchanged — only what each element is.
2. **`resolve_project_cache_test.go` (+15/−6)** — the existing literals become typed refs, and one case is added for the new dimension: the *same* candy ref requested from **two different box scopes** must not share a cache key. That is the `#739` constant-scope collision, asserted rather than assumed.

Without the scope in the key, two deploys pulling the same candy ref from different boxes would collide on one entry and be served an envelope resolved for the other scan.
