# 2026.293.0443 — feat(build): push each built image to the local charly OCI registry (the base-input half)

## Summary

Makes a locally built image resolvable to **buildkitd** for the next stage's `FROM`. The drive bridged only the *output* of a build into the run engine's store (`LoadExport`); the *input* half was missing, so a base built earlier in the same run was invisible to the daemon and the resolve went upstream — `403` for an internal tag.

Three parts:

1. **`driveConfig.RegistryMirror`** (from `CHARLY_BUILD_REGISTRY_MIRROR`) handed to `buildkitdrive.Ensure`; the sdk (`v0.2026293.417`, from `opencharly/sdk#428`) renders the mirror pair into `buildkitd.toml`.
2. **The push**: after `LoadExport`, the built image is pushed to that registry under the **same `FullTag`** (`localRegistryRef`), so the next stage's `FROM` resolves from the mirror.
3. **`registry.go`**: the drive owns the registry's *lifecycle* — reuse anything answering `GET /v2/`, else start `registry:2` on the mirror's host:port through the **configured run engine** and wait for readiness.

## Module pins in this diff (accounted)

`go.mod`/`go.sum` move **two** requirements, both consequences of point 1:

- `github.com/opencharly/sdk` `v0.2026287.2213` → **`v0.2026293.417`** — the published, tagged `opencharly/sdk#428` (this is what makes `DaemonOptions.RegistryMirror` exist; the earlier branch state used a local `replace`, which is gone).
- `github.com/opencharly/spec` `v0.2026287.1848` → `v0.2026289.611` — `go mod tidy`'s minimum-version selection after the sdk bump (the sdk requires the newer spec). Transitive, not a hand-pick.

Unit (`candy/plugin-build/registry_test.go`, new):

- `localRegistryRef` — three ref shapes, plus the invariant that the mapped ref stays under the mirror prefix;
- `registryAnswers` — against a live `httptest` server: `200` and `401` count as answering, a `404` and a closed port do not;
- `ensureLocalRegistry` — an empty mirror is a no-op (existing behaviour untouched), and a mirror without `host:port` is rejected by name.

## Rulebook compliance

- **R0** — `build`, `plugin` and `go` skills loaded before editing the drive.
- **R1** — root-caused to the disjoint stores (output bridged, input not), not to the CDN.
- **R2** — every site covered: option, ensure call, push, lifecycle.
- **R3** — one mapping helper, one engine accessor (`container.EngineBinary`), one probe. The lifecycle carries NO engine-specific flag: the leftover container is cleared with `<engine> rm -f` (portable across podman/docker/nerdctl) rather than `podman run --replace`.
- **R4** — **stated honestly**: there IS a bounded readiness wait, and it is deliberate and named — `registryReadyWindow` (30 s) polling every `registryReadyPoll` (500 ms), each probe bounded by `registryProbeTimeout` (2 s), all cancelled by the build context. It is not a blind retry: it is waiting for a container the drive itself just started to answer its own API, and the failure path names the address and the window. Nothing hides a race; the alternative (sleep, or assume ready) would be the band-aid.
- **R5** — no legacy path; an empty `RegistryMirror` starts nothing and pushes nothing.
- **R6** — branch only.
- **R7** — the tests fail without the change (the mapping did not exist; the probe had no status contract), and the live run proves the end-to-end behaviour.
- **R8** — the artifacts observed are the registry's catalog/tags and the daemon's resolve line.
- **R9** — **honestly**: the live run used a *development* consumer build (no CalVer stamp to assert). The stamped consumer run is `opencharly/charly#985`.
- **R10** — the assembled bed belongs to the consumer and is filed, not silently deferred.
- **CONC** — the push happens after that image's build completes and before its build lock is released, so two builds of one image cannot interleave repository writes; distinct images keep distinct locks.
- **HC** — N/A: no harness config, alias, hook or probe surface touched.
- **DISP** — N/A: no `disposable:` target is created, mutated or destroyed. Note: the registry container has a deterministic name and is cleared with `<engine> rm -f` before start, so an interrupted run's leftover cannot block the next build — portably, since `podman run --replace` is podman-only.
- **PIL** — the two module pins above; no gitlink or umbrella pin moves here (charly's pins follow in their own PR).
