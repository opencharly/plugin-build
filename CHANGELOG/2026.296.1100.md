# 2026.296.1100 — feat(build): the charly image store, annotated exports, and oci-layout parents (#36)

## Summary

W3.6 of opencharly/opencharly#481: the build's output becomes an engine-neutral artefact, and the
engine is no longer part of how an image is named or how a parent box is found.

**What changed**

* **The charly image store** (`candy/plugin-build/imagestore.go`, new). Every build's export is
  written into one engine-neutral OCI layout at `$XDG_DATA_HOME/charly/images/` (override
  `CHARLY_IMAGE_STORE_DIR` for a disposable target): one `index.json`, each manifest annotated
  **`io.containerd.image.name=<FullTag>`** and **`org.opencontainers.image.created`**, plus the
  tag-only `org.opencontainers.image.ref.name` kept for readers that expect it. Blobs are
  content-addressed and copied once; the index is rewritten atomically under a lock held in the
  state root (never inside the store tree).
* **A tag-free engine import** (`buildkit.go: importExport`). The export is annotated *before* the
  import, and the import is a plain `<engine> load -i <archive>` followed by a **verification**
  that the reference resolves. The `load → tag → verify` dance is retired. The engine binary and
  the existence probe both come from the capability table (`container.EngineBinary` +
  `EngineCapabilityFor(...).ImageExistsArgv`) — no engine word literal on the build path.
* **`--oci-layout` parents** (`buildkit.go: buildImage`). For each box the drive reads
  `ARG BASE_IMAGE=<ref>` from the generated Containerfile; if that ref is in the store, the store is
  handed to the daemon as `buildkitdrive.Build.OCILayouts` and the base is bound as a named context
  (`--opt context:<ref>=oci-layout://charly@sha256:<manifest>`). The registry remains the fallback
  when the parent is absent locally. This wires the previously caller-less `Build.OCILayouts`
  (sdk#433).
* **No engine literals** (`ensure.go`). `podman pull` / `podman tag` / `podman` existence probes are
  now `enginePull` / `engineTag` / `kit.LocalImageExists(runEngine, …)`, resolved through the
  capability table; an empty engine means the default engine rather than the literal `"podman"`.
* `go.mod`/`go.sum`: sdk `v0.2026293.417 → v0.2026296.803` (the tagged release carrying
  `Build.OCILayouts`, sdk#433) and its required spec `v0.2026295.2356`.
* Prose corrected on the changed surface: `README.md` and the `plugin-build:` candy description
  no longer claim a `LoadExport` tag step or that the plugin "runs podman directly".

**Every file in the diff:** `README.md`, `candy/plugin-build/README`-adjacent `charly.yml`,
`buildkit.go`, `ensure.go`, `imagestore.go` (new), `go.mod`, `go.sum`, and four test files
(`buildkit_live_test.go`, `ensure_alias_test.go`, `imagestore_test.go` (new),
`imagestore_live_test.go` (new)).

**Deliberately NOT in this PR** (cross-repo; filed, with numbers, below): `--engine`, the
`--tag > box tag > defaults.tag > auto` head, and `charly clean` pruning of the store.

**Spike (RDD, before implementation).** On this host, buildkit 0.34.1: `--output
type=oci,name=<ref>` writes `io.containerd.image.name=<full-ref>` + `ref.name=<tag only>` +
`created`; `podman load` applies the full ref with no tag step; the same archive without `name=`
lands `Loaded image: sha256:…`. A child solved with `--oci-layout charly=<store> --opt
context:<base>=oci-layout://charly@sha256:<digest>` builds while `ghcr.invalid` is unreachable; the
same child without the override fails `dial tcp: lookup ghcr.invalid: no such host`. That spike is
what selected the named-context form (a literal `FROM oci-layout://…` is rejected by the Dockerfile
frontend as an invalid reference).

## Filed issues

* opencharly/sdk#458 — `storekit` has no data root, so `$XDG_DATA_HOME/charly/images` has no
  resolver. Worked around locally in `imagestore.go` (with the issue named in the comment); the
  workaround is deleted when the root lands.
* opencharly/plugin-box#61 — `charly box build --engine` needs `spec.BuildRequest.Engine` + a CLI
  flag, and `--tag` cannot beat a box/defaults tag because `dispatchBuild` pre-fills the CalVer, so
  the drive cannot tell an explicit `--tag` from `auto`.
* opencharly/plugin-clean#21 — `charly clean` (`keep_images`) must prune the charly image store's
  entries and unreferenced blobs as well as engine stores; today nothing reclaims them.
* opencharly/sdk#457 (existing, open) — `ResolvePodEngine` / `ResolveContainerdTarget`. Not tagged,
  so this change keeps the existing resolved-run-engine selection and adds **no** second selector.
