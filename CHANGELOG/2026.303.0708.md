# 2026.303.0708 — fix(build): the live proof's comment names the mechanism the drive actually runs

## Summary

**Predecessor:** opencharly/plugin-build#40 — the stale-comment issue, filed by the
`stage_parallelism` fan-out's closing sweep and CLAIMed by this session. This PR is that issue's
fix. Closes #40.

The live proof's header comment carried two present-tense claims that had both stopped being true,
and they sat in one comment block.

**Cluster 1 — the migration claim.** The header justified driving the drive directly from the
module with three identifiers the contract no longer has:

> ⚑ Why this lives in the module rather than as an assembled `charly box build`: the plugin is
> COMPILED INTO charly, so assembling charly requires every pinned plugin to compile against the
> new contract — and they have not all migrated yet (measured: `plugin-box` v0.2026272.2039 fails
> on `spec.BuildRequest.PodmanJobs`, `rt.BuildEngine`, `spec.BoxConfig.PodmanJobs`).

`PodmanJobs` was renamed to `stage_parallelism`, and `rt.BuildEngine` was retired outright — the
builder is BuildKit, which is not a container engine, so the contract carries no builder selector
at all. The producer leg landed on 2026-10-28 (`opencharly/plugin-box#66`) and the assembled
consumer an hour later (`opencharly/charly#1082`); the assembled build is green and the ecosystem
HAS migrated.

**Cluster 2 — the bridge description.** The same block described the bridge as
"load → tag → verify" and named "the tag re-application" as the duty whose loss would break every
downstream verb; the assertion's own comment and its failure message ("the tag duty failed")
repeated it.

There has been no tag step since the charly image store landed (`c79ee55`): the export is
annotated with `io.containerd.image.name=<FullTag>`, the annotation is what names the image, and
the import verifies the reference resolves.

**The RCA for this finding.**

- **Mechanism.** The comment asserted a fact about the ecosystem at the time it was written
  (2026-10-23), and the ecosystem moved: the rename landed and the retirement landed, so the
  identifiers it cited stopped existing. The bridge half was the same shape one step older — it
  described a "load → tag → verify" duty that the image store replaced with a naming annotation,
  and it was never revisited after that landing. Both are present-tense claims about a contract
  that has moved on.
- **Missed control.** Nothing tied a comment's factual claims to the contract they describe. The
  three live tests in this module assert the drive's BEHAVIOUR against a real daemon, but no
  control read the prose and checked it against the contract — so the comment stayed green while
  the code around it proved the comment false.
- **Blast radius.** A reader is told the ecosystem cannot yet be assembled, so the live proof must
  stay in the module, and that a tag step is a named duty whose loss breaks every downstream verb.
  The first teaches an arrangement that the assembled build already supports; the second teaches
  the spelling of a step that no longer exists, and points at the wrong mechanism — the naming
  annotation — as the thing whose loss breaks the downstream verbs.
- **Root fix.** The comment now states the DURABLE reason the drive is driven directly from the
  module — the plugin is compiled into charly, so an assembled build couples this proof to every
  other pinned plugin's release, and would answer "does the whole product assemble" rather than
  "does THIS drive work" — and it names the bridge as it runs: annotate → store → load → verify.
  The assertion's comment and its failure message now name the mechanism the sibling live test
  already names, so the two live proofs speak one vocabulary.
