# 2026.309.2032 — fix(ensure): build into the run engine the caller asked for, and alias its own produced ref

## Summary

`build:ensure`'s local build fallback could not deliver an image into a
non-default run-engine store. `runBoxBuild` took `driveConfig.RunEngine` from
`build:resolve`'s reply (the HOST runtime engine), ignoring the
`#BuildEnsureRequest.run_engine` the caller passed. A `pod:` deploy authored
`engine: containerd` therefore had its locally-built image bridged into podman;
the alias step then failed with `image not found` against the containerd
store, and the deploy never reached `charly config`.

This threads the requested run engine through an internal
`runBoxBuildWithEngine`: the BuildKit export is imported into the store the
deploy will actually run on. `runBoxBuild` keeps its old behaviour (empty
override), so `build:box` / `build:generate` are unchanged. The REMOTE-REF
fallback (`ensureRemoteRef`) also changes: it passes the requested run engine
to the same override and aliases via `builtRefForBox`. `buildEngineFor` is the
pure precedence rule, unit-tested both ways.

R5: the diff replaces the two alias CALLBACKS, not the two resolvers. Neither
resolver is dead; the executed grep (non-test files) shows the live call sites:

## Change classification

Internal build-drive behavior only: `build:box`/`build:generate` keep the
host-runtime engine; `build:ensure`'s local fallback now builds into the run
engine it was asked to serve. No wire/schema change, no authored key change.
Rollback: revert this PR; the previous host-engine build and the alias failure
return.

**Breaking change + rollback:** none — the override is empty unless a caller
explicitly requested a run engine.
