# 2026.322.1325 — feat(build)!: write built images to storekit's registry store

## Summary

`plugin-build` no longer owns an OCI image store. The layout (`oci-layout` + one `index.json` +
`blobs/<alg>/<digest>`), the streamed blob copy, the atomic index rewrite and the cross-process
index lock now live in `sdk/storekit`, where the image resolver reads the same entries
(opencharly/sdk#556), and this repo keeps only what a build owns and calls the shared store —
opencharly/sdk#460 step 3, "reduce `plugin-build`'s file to the build-specific annotations and call
the shared store".

**Deleted, because the store is not this repo's business:** `imageStoreDir()` and its
hand-resolved `$XDG_DATA_HOME` (the WORKAROUND the file itself called out), `CHARLY_IMAGE_STORE_DIR`,
the `oci-layout` marker writer, the `index.json` read/merge/rewrite, the streamed blob copy, the
layout-directory preparation, and the store-index lock.

**Kept, because only a build has it:** choosing the reference — `containerfileStageRefs` /
`FromRefs` / `BaseRef`, now driven by `bindStoreContexts`, which asks the store for `Lookup` and
`Dir` instead of composing a path — and naming the export. `annotateExport` still writes
`io.containerd.image.name` (plus the tag-only `org.opencontainers.image.ref.name` and the build
instant) into the archive, because `storekit.ImageStore.Add` refuses an archive that does not
already name its reference, and the kit emits a bare `--output type=oci,dest=<file>`. That is the
one thing `Add` cannot do for the build's export.

**Where the store is now:** the `registry` named store under the cache root, resolved by
`storekit.StoreDir`. `D-STORE-1` (`DESIGN.md:2482`) blesses exactly one relocation lever —
`CHARLY_CACHE_DIR` — so the image-specific override is deleted rather than reworded;
`plugin-clean`'s retirement record keeps `<cache root>/images`, and nothing here writes to a store
named `images`.

## Change classification

Plugin-library change: Go plugin source, no schema, no image, no bed definition. `build:box`,
`build:generate` and `build:ensure` keep their inputs, replies and plan steps.

**Breaking change + rollback:** the retired `CHARLY_IMAGE_STORE_DIR` no longer relocates anything and
the pre-change `$XDG_DATA_HOME/charly/images` tree is not migrated, so an image built before this
change is no longer found by the drive — it is rebuilt on next use, and a host that relied on the
override now relocates only through `CHARLY_CACHE_DIR`. Rollback is reverting this commit: the old
layout was never deleted, so those images are still on disk at their original path and resolve again
once the previous code returns.
