# 2026.327.1034 — fix(build): remove the OCI export on every exit path, not only a successful bridge

## Summary

`charly box build` removed each image's staged OCI export **only after a successful bridge**, so
every other exit — a failed build, a failed `annotateExport`, a failed `store.Add`, a failed
engine load, a cancellation — left a partial or 0-byte archive behind under a name no later build
reuses. On a host with a build history that grows without bound, and the export eventually fails on
a full disk under a path nobody recognises as a leak (opencharly/plugin-build#64: 71 archives,
68 GiB, plus 0-byte residues from failed exports).

This change gives the archive one lifecycle, owned in one place:

- **The cleanup is a `defer` installed the moment the destination is known**, and its error is
  **joined** onto the build's own (Go 1.20 `errors.Join`), so the archive's removal can never
  replace the reason a build failed — the ENOSPC case is exactly where both exist.
- **One rule, not a second copy**: the removal is `buildkitdrive.RemoveExport` from the SDK,
  released as `github.com/opencharly/sdk v0.2026327.1021` (producer-first: opencharly/sdk#624
  merged and tagged before this pin bump). `go.mod` moves to that release.
- **The `spec` module moves with it, and that is accounted for here**: `github.com/opencharly/spec
  v0.2026325.913 → v0.2026327.605`. It is a DIRECT require of this module, and it moved because the
  SDK release pins exactly that version, so MVS raised the shared pin:

  ```
  $ go list -m github.com/opencharly/spec
  github.com/opencharly/spec v0.2026327.605
  $ grep opencharly/spec go.mod
  38:	github.com/opencharly/spec v0.2026327.605
  $ grep opencharly/spec $(go env GOMODCACHE)/github.com/opencharly/sdk@v0.2026327.1021/go.mod
  18:	github.com/opencharly/spec v0.2026327.605
  ```

  The full `go test ./...` run above (8.853s, green) compiles and exercises the spec types this
  plugin consumes at that version.
- **The remove-only-on-success block is deleted**, not kept beside the defer.
- **The build/bridge command runner becomes a package var**, so the FAILURE path is testable: the
  bridge can be made to fail while the build still runs.
