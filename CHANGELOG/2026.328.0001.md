# 2026.328.0001 — fix(build): keep the captured buildctl output in the failed-build error

## Summary

A failed build no longer discards its own diagnostics. `buildkitdrive.ExecRunner.Run` captures `buildctl`'s combined stdout+stderr — and this call threw it away, wrapping only `exit status 1`:

```diff
-	if _, err := runner.Run(ctx, buildkitdrive.BuildctlBinary, args...); err != nil {
-		return fmt.Errorf("building %s: %w", box.Name, err)
-	}
+	out, err := runner.Run(ctx, buildkitdrive.BuildctlBinary, args...)
+	if err != nil {
+		return fmt.Errorf("building %s: %w\n%s", box.Name, err, tailLines(out, 60))
+	}
```

**Why it matters (measured).** opencharly/charly#1255: a `pacman` step in a base-stage `RUN` failed, the step log ended at the `RUN` line, and the buildkitd daemon log carried no error either — because the only artifact that ever held the text was the in-memory `out` this line dropped. Six checks were spent disproving hypotheses (`--progress plain` already explicit; daemon log clean; mirrors reachable; no stale `db.lck`) before the discard was found by reading this file. The same discard hides every future build failure in this repo's path.

`tailLines` keeps the **last** 60 lines — the failing step's own line, not the leading progress — and never emits a trailing newline.

## How tested

```

$ go test ./... -run TestTailLines -v
```

`TestTailLines` pins the truncation semantics; `TestBuildFailure_CarriesTheCapturedOutput` asserts the error carries the step's line and leaves no trailing newline on empty output; and — the review's actual requirement, which I missed twice — `TestRunBuildctl_PutsTheCapturedOutputInTheError` exercises the CALL SITE: the build call is the method `runBuildctl` (capture → `buildFailure`), and a runner that fails only `buildctl` is injected, with the returned error asserted to contain the captured `#12 ERROR: …` line. Reverting the method to `if _, err := runner.Run(...)` fails that test while the helper tests stay green.

```
--- PASS: TestTailLines (0.00s)
--- PASS: TestBuildFailure_CarriesTheCapturedOutput (0.00s)

```

**What is not proven here:** the error appearing in a real build. This module is compiled into charly, so a charly dependency bump and release must land before a host build uses it; the live proof is the next build after that, which should print the pacman error that #1255 is about. The commit is therefore `analysed on a live system`, not `fully tested and validated`.
