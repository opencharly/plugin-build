# 2026.331.1456 — feat(build): render defaults.buildkit into the buildkitd daemon settings

## Summary

The project's authored `defaults.buildkit` (spec `#Buildkit`) now reaches the build daemon. `buildkitdrive.Ensure` was called with only `max-parallelism` and the registry mirror; the drive now maps the whole authored surface onto `buildkitdrive.DaemonOptions`:

- `process_mode`, `max_parallelism`, `snapshotter`, `no_process_sandbox`;
- the GC budget (`reserved_space` / `max_used_space` / `min_free_space`) and `gc: false`;
- per-record `gcpolicy` entries, `registry_mirror`, and the raw `extra` TOML;
- an unauthored field keeps the drive's fallback (the resolved `stage_parallelism`, the `CHARLY_BUILD_REGISTRY_MIRROR` env), and an unauthored GC budget takes sdk's **100 GB default** — the measured fix for the cache eviction in opencharly/charly#1292.

Dependencies are the released producer tags: **sdk `v0.2026331.1440`** (the `DaemonOptions` surface + the 100 GB default) and **spec `v0.2026331.1221`** (`#Buildkit`), in `go.mod`/`go.sum`.

**One real break the version bump surfaced, fixed here.** spec#445 made `CandyStageDirName` **content-addressed** (`<name>.<sha256[:16]>`) with the version-keyed `<name>.<version>` only as a fallback, and `remote_candy_copies_test.go` hardcoded `marker.2026.181.1430`. The package gate caught it (`remote candy source not staged at …/marker.2026.181.1430/copied.dat`). The test now asks the **same `deploykit.CandyStageDirName` the emitter uses**, so the guard tracks the contract rather than a spelling; the production path was already consistent (it calls that function).

### Spike

**RCA claim:** a project must be able to author the daemon settings, and the TOML the drive renders from them must be accepted by a real `buildkitd`.

**Candidates:**

- **A. Map each authored field onto `DaemonOptions` (chosen).** Instrument: render the **PR's own path** — `driveConfig.daemonOptions()` → `buildkitdrive.DaemonConfig` — then start a real rootless `buildkitd` with exactly that file.

  The artifact, produced by the mapping (test probe: `buildkitdrive.DaemonConfig(c.daemonOptions())`):

  ```
  # Rendered by sdk/buildkitdrive. Do not hand-edit: the drive writes it from the
  # resolver's roots on every ensure.
  [worker.oci]
    process-mode = "sandbox"
    max-parallelism = 8
    snapshotter = "overlayfs"
    noProcessSandbox = true
    gc = true
    reservedSpace = "40GB"
    maxUsedSpace = "80GB"
    minFreeSpace = "5GB"

  [[worker.oci.gcpolicy]]
    all = true
    maxUsedSpace = "60GB"
    filters = ["type==source.local"]
  ```

  The daemon started with it — full log, no parse/unknown-field error:

  ```
  $ rootlesskit --net=host buildkitd --rootless --root <tmp> --addr unix://<tmp>/b.sock --config mapped-real.toml
  level=warning msg="NoProcessSandbox is enabled. Note that NoProcessSandbox allows build containers to kill ..."
  level=warning msg="CDI setup error /etc/buildkit/cdi: failed to monitor for changes: no such file or directory"
  level=warning msg="failed check for fsverity support" error="enable fsverity failed: inappropriate ioctl for device"
  level=info msg="found worker \"zny8dlhcbnx4kanxt9kb3jnhh\", labels=map[... oci.process-mode:no-sandbox ... worker.snapshotter:overlayfs ...]"
  level=info msg="found 1 workers, default=\"zny8dlhcbnx4kanxt9kb3jnhh\""
  level=info msg="running server on .../b.sock"

  $ buildctl --addr unix://<tmp>/b.sock debug workers
  ID                              PLATFORMS
  zny8dlhcbnx4kanxt9kb3jnhh       linux/amd64,linux/amd64/v2,…,linux/arm/v6
  # exit 0
  ```

  **The worker labels are the proof the settings TOOK EFFECT**: `oci.process-mode:no-sandbox` (from `noProcessSandbox = true`) and `worker.snapshotter:overlayfs` (from `snapshotter`). The mixed casing (`process-mode`/`max-parallelism` kebab, the GC fields camelCase) is buildkitd's OWN accepted form — this daemon started from exactly that file, so it is not a renderer defect and nothing is silently ignored. A `[[worker.oci.gcpolicy]]` entry is present and accepted in the same file.

- **B. Expose only the raw `extra` TOML (no first-class fields).** Rejected by the spec spike that produced `#Buildkit` (opencharly/spec#447): an untyped blob cannot be validated or defaulted, so the 100 GB GC default — the half of #1292 that keeps the cache — could not exist, and a typo would be a silent no-op. It survives as the `extra` escape hatch.

- **C. Ignore `defaults.buildkit` and rely on the sdk defaults alone.** Rejected: it makes "all buildkit settings configurable in `charly.yml`" false (the explicit ask), and leaves `process_mode`/`snapshotter`/`gcpolicy` unreachable. `TestDaemonOptions_MapsAuthoredBuildkit` is the guard A needs and C would not have.

**On the casing question:** the mix is deliberate and verified above — `process-mode` and `max-parallelism` are buildkitd's TOML spellings for those two worker keys (the same spellings its own config docs/examples use), while the GC/worker fields are camelCase. A daemon started from the exact rendered file reports the applied labels and exits 0, which is the evidence that matters; a hand-typed variant was never relied on.

**Measured detail that corrected a doc claim:** appending a duplicate table through `extra` is not "disallowed by us", it is rejected by the daemon:

```
$ # same config, plus: [worker.oci]\n  oom-score-adj = 100   (the `extra` block)
buildkitd: toml: table oci already exists
failed to parse config
exit status 1
```

That is exactly what `DaemonOptions.Extra`'s comment now says (extend, never redefine, the managed block).

**Winner:** A. **RCA verdict:** confirmed — the mapped surface renders to TOML that a real daemon starts with, and the one integration break in the bump (the content-addressed stage dir) was caught and fixed.
